# `llm-core-v1` compatibility profile

Date: 2026-07-22

TorchLite does not claim whole-library PyTorch parity. `llm-core-v1` is the
smaller, executable promise: common dense decoder-only transformer teaching
code can train in a JupyterLite/Pyodide worker through familiar `torch`,
`torch.nn`, `torch.nn.functional`, and `torch.optim` names.

PyTorch documents more than 3,500 built-in operator variants before accounting
for the dispatcher, devices, compilation, distributed execution, mixed
precision, sparse and quantized layouts, and extension APIs. Reproducing that
surface in a browser would be a different project. A trace-driven profile is
both achievable and honest: implement the primitives actually reached by
representative LLM programs, then test their results and gradients against real
PyTorch.

## Supported in version 0.2

| Area | Executed surface |
|---|---|
| Tensor layout | `view`/`reshape`, `transpose`, `permute`, `contiguous`, `flatten`, `split`, `chunk`, slicing |
| Tensor math | broadcast arithmetic, reductions, batched `matmul`, `exp`, `log`, `sqrt`, `tanh`, `softmax`, masks |
| Modules | recursive `Module`, `ModuleList`, `ModuleDict`, `Sequential`, `apply`, `Linear`, `Embedding`, `LayerNorm`, `RMSNorm`, `GELU`, `Dropout` |
| Functional | `cross_entropy` with `ignore_index`, causal scaled-dot-product attention, layer norm, GELU, dropout |
| Training | reverse-mode autograd, `AdamW`, L2 gradient clipping, `state_dict` round trip, train/eval propagation |
| Validation | one-block Tiny GPT runs unchanged under TorchLite 0.2 and PyTorch 2.13; losses differ by less than `1e-4` |

The executable contract is
[`tests/test_llm_core.py`](../tests/test_llm_core.py). The committed reference
fixture was generated by running that same file with PyTorch 2.13 on CPU. The
browser contract is [`04-tiny-gpt.ipynb`](../jupyterlite/content/04-tiny-gpt.ipynb).

## Deliberately outside version 0.2

- CUDA, MPS, distributed training, multiple devices, and custom extensions.
- `torch.compile`, TorchScript, the dispatcher, and graph transforms.
- sparse, quantized, complex, and mixed-precision tensors.
- fused optimizers/kernels, FlashAttention, checkpointing, and production
  checkpoint formats.
- exact coverage of arbitrary PyTorch programs or all shape/error corner cases.

Unsupported behavior should fail explicitly. A matching name without matching
numerics, gradients, broadcasting, dtype, or state semantics is not parity.

## Related implementations

| Project | What it demonstrates | Relationship to TorchLite |
|---|---|---|
| [WgPy](https://github.com/mil-tokyo/wgpy) | NumPy/CuPy-like WebGPU and WebGL arrays integrated with Pyodide, including synchronous Python-facing operation | Closest backend and worker-synchronization reference; not a PyTorch training API |
| [webgpu-torch](https://praeclarum.org/webgpu-torch/docs/) | TypeScript/WebGPU tensors and reverse-mode autograd inspired by PyTorch | Useful small autograd/kernel design; JavaScript rather than Pyodide Python |
| [Burn](https://github.com/tracel-ai/burn) | Rust tensor/autodiff framework with a mature `wgpu` backend | Strong WebGPU kernel reference; not PyTorch source-compatible |
| [TensorFlow.js](https://github.com/tensorflow/tfjs) | Mature browser training across CPU, Wasm, WebGL, and WebGPU backends | Proves browser training is viable, but requires the TensorFlow.js API |
| [torch.js](https://torchjs.org/docs) | Advertises a broad TypeScript PyTorch-like WebGPU API | Ambitious comparison point, but its documentation currently says it has not been released |
| [torch-webgpu](https://pypi.org/project/torch-webgpu/) | Compiles/dispatches native PyTorch work to WebGPU-oriented kernels | Adjacent compiler/backend work; it does not provide PyTorch inside Pyodide/JupyterLite |

Inference projects such as ONNX Runtime Web, Transformers.js, and WebLLM solve a
different problem: running exported or packaged models rather than preserving
an editable Python training notebook.

## Next parity method

1. Trace representative Zero-to-Hero, nanoGPT, and minGPT programs under real
   PyTorch and record every reached operator, overload, module, and state API.
2. Add only the missing high-frequency primitives to the versioned profile.
3. For every primitive, compare forward values, gradients, broadcasting, error
   behavior, and state against PyTorch fixtures.
4. Keep NumPy/Wasm as the correctness backend and route the same primitive
   registry to WebGPU; never silently fall back from a claimed GPU path.
5. Promote a workload only after it passes locally and in an actual browser.

That is the practical 20/80 route: not 20% of PyTorch's namespace, but the much
smaller set of primitives beneath most educational dense-transformer code.
